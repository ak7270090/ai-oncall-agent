# Coding Guidelines

Rules for all code in this repository, whether written by a person or generated by
an AI assistant. A change that breaks a rule needs a stated reason in its commit
message.

## 1. Configuration, not constants

- Every value that could differ between environments (URLs, ports, model names,
  timeouts, retry counts, limits) lives in the app's settings module
  (`config.py`, or `settings.py` for the single-file sample services),
  built with `pydantic-settings` and overridable with an environment variable
  or `.env`.
- Automation values are variables at the top of the `Makefile` (`?=`, so
  `make <target> VAR=value` can override them), not literals inside recipes.
- Document every setting in that app's `.env.example`.
- Fixed values that are not settings (enum-like names, protocol and vocabulary strings,
  tool argument limits, fixed user-facing messages) live in a `constants.py` (the domain's,
  or the app's for values several domains use),
  never as module-level literals scattered across files. Use `StrEnum` for named sets
  (`Step`, `McpTool`, `Metric`) in both apps, and use its members in code
  (`Metric.ERROR_RATE`, not `"error_rate"`). Exception: an MCP tool argument is typed
  as a `Literal` built from the enum (`MetricName`), so the JSON Schema shows an inline
  `enum` rather than a `$ref`. Messages that embed variables stay as f-strings where
  they're raised.
- A message that more than one implementation produces (real and fake backend) is
  built in one shared function next to the error type (`k8s/cluster/access.py::
  not_found_error`), so the implementations can't drift apart.
- Values that define an API contract (such as a tool's maximum `lines`) are named
  module-level constants (`MAX_LOG_LINES`). Never leave an unexplained literal
  in logic.
- Read settings with `get_settings()` or FastAPI `Depends`, never `os.environ`
  in app code.

## 2. Secrets

- Secrets live only in `.env`, which git ignores. Never put them in code,
  `.env.example`, tests, logs, error responses or docs.
- Type secrets as `SecretStr` and call `.get_secret_value()` only where the
  secret is handed to a client.
- Don't send upstream error text (LLM provider, HTTP) to API callers. Log it on
  the server and return a generic message.

## 3. LLM access is provider-agnostic

- App code never imports `openai`, `anthropic` or any other provider SDK.
- Chat models are built only through `llm/chat_model.py::create_chat_model`
  (LangChain `init_chat_model`). To switch provider or model, change `LLM_MODEL`
  (`"<provider>:<model>"`) and `LLM_API_KEY`. No code changes.
- Orchestration uses LangGraph. Tools reach the LLM as LangChain tools built
  from MCP tools (`mcp_client/langchain_tools.py`).

## 4. App boundaries

- `mcp-platform/server/` and `ai-server/` never import each other. They meet only
  through MCP over HTTP. Each has its own venv, requirements and settings.
- Put infrastructure logic (Kubernetes, Prometheus) only in the MCP server, and
  LLM logic only in the AI server.
- A local package must not share its name with an installed library (hence
  `mcp_client/`, not `mcp/`).

## 5. Structure and reuse

- The repository is organized by purpose: `ai-server/` (the agent), `mcp-platform/`
  (`server/` and `gateway/`: the tool side of MCP), `lab/` (`services/` and
  `kubernetes/`: the system the agent investigates), `evals/`, `docs/`. A new top-level
  folder needs a purpose none of these has.
- Kubernetes manifests follow Kustomize's base + overlays: `base/` holds one folder per
  workload (`payment-service/{deployment,service,configmap}.yaml`, `secret.env`), never
  folders per kind; `incidents/` are the overlays. A component's own manifests live with
  it (`mcp-platform/server/deploy/`) and the base includes them.
- Compose files use Docker's names: `compose.yaml`, overlays `compose.<purpose>.yaml`.
- Every Python project has a `pyproject.toml` (project metadata, pytest settings, ruff
  `extend` of the root `ruff.toml`); pinned dependencies stay in `requirements*.txt`
  for the Dockerfiles.
- The README says what the project is and how to run it; feature explanations go in
  `docs/<topic>.md`.
- Organize by **domain**, not by file type. A domain folder holds everything about one
  feature, in files with fixed names: `router.py` (HTTP routes), `schemas.py` (request
  and response models), `dependencies.py` (FastAPI dependencies), `constants.py`,
  `service.py` (the entry point of its logic), plus modules named after their job.
  ai-server: `investigation/`, `actions/`, `auth/`, `llm/`, `mcp_client/`; mcp-server:
  `k8s/`, `prometheus/`, `access/`.
- Flat is better than nested: something that is one module stays a module
  (`config.py`, `tracing.py`, `health.py`, `errors.py`); a folder needs at least two
  modules that belong together. Split a domain into subfolders only when it has
  several jobs of several files each (`investigation/workflow/`,
  `investigation/evidence/`).
- `__init__.py` only describes the package (a docstring). Import from the module that
  defines a name (`from investigation.models import IncidentReport`), so every import
  says where the code is.
- Constants live with their domain (`investigation/constants.py`); the app's top-level
  `constants.py` keeps only values used across domains (trace names, health statuses).
- Build objects in factory functions (`create_app`, `build_k8s_server`,
  `create_chat_model`, `build_investigation_graph`) so tests can build their own.
- Group the MCP server by tool set, not by layer: `k8s/` and `prometheus/` each hold
  their tools, backends, models and fakes; only what both use is shared
  (`base_server.py`, `tool_definitions.py`, `access/`, `config.py`, `constants.py`,
  `fake_incident.py`). Each MCP server has its own entry point (`k8s/server.py`,
  `prometheus/server.py`); no setting decides what a process is.
  Each tool module returns its tool definitions, and its server registers them.
- Before writing a helper, check whether one already exists. Extend it rather
  than copying it.
- Don't write speculative code: no unused parameters, abstractions or files for
  "later". Add them in the phase that needs them.

## 6. Naming

- Names say what a thing is or does: `connect_to_mcp`, `load_langchain_tools`,
  `MAX_LOG_LINES`, `mcp_client`. Avoid `data`, `obj`, `tmp`, `c`, `x`.
- Functions start with a verb. Booleans read as a yes/no question: `is_error`,
  `is_condition_met`, `completed`. Use these prefixes consistently:
  - `to_…` converts one object into another (`_to_pod_detail(raw)`, `to_markdown()`)
  - `build_…` / `make_…` assembles a new value (`build_query`, `build_label_selector`,
    `_make_healthy_container`)
  - `extract_…` / `parse_…` pulls data out of something (`extract_result_text`, `parse_tool_output`)
  - `get_…` / `list_…` / `query_…` reads from a source (`get_pod`, `query_prometheus`)
  - `create_…` makes an object that holds a resource, a client or an app
    (`create_app`, `create_reader`, `create_chat_model`); `build_…`
    assembles a value from parts without side effects (`build_query`,
    `build_investigation_graph`, `build_mcp_connector`)
  - FastAPI dependencies: `get_…` functions, used through `…Dep` aliases
    (`get_current_user` → `CurrentUserDep`)
  
  Not `_pod_detail(raw)`, `result_text(result)` or `holds(condition)`.
- Name files after their contents: `connection.py`, `collection_steps.py`,
  `mcp_toolbox.py`, not `misc.py`, `collection.py` or `signals.py`. A module name
  shouldn't repeat or collide with another layer's name: `mcp_client/langchain_tools.py`
  (the MCP → LangChain adapter), not `mcp_client/tools.py` next to `mcp-platform/server/tools/`.
- Files in the same folder never differ only by extension or a letter.
  `prometheus-deployment.yaml` (Kubernetes manifest) and `scrape-config.yaml`
  (Prometheus config), not `prometheus.yaml` and `prometheus.yml`. Kubernetes manifests
  are named after what they contain.
- Keep fake implementations out of the real ones' files: each `MCP_BACKEND=fake` backend
  sits in its own module next to the real one it replaces (`k8s/cluster/fake.py`,
  `prometheus/metrics/fake.py`), and the canned incident both serve is
  `fake_incident.py`. Test-only fakes stay in `tests/` (`tests/fakes.py`).
- Small pure functions go in a module named after what they do
  (`investigation/evidence/analysis.py`: the rules that read evidence). `helpers.py`
  only for a few small functions with no better common name (`prometheus/helpers.py`).
  Never a project-wide `utils.py`.
- Don't create a file for a single small function. Put it where it belongs,
  e.g. formatting a report is `IncidentReport.to_markdown()` in `investigation/models.py`.
- Name functions after their purpose in the domain, not a metaphor:
  `collect_namespace_overview`, not `sweep`. A reader should know what a function
  does without opening it.
- Avoid functions defined inside functions. Prefer a class whose methods share
  dependencies (`InvestigationNodes`). Exceptions: MCP tool factories
  (`build_pod_tools`) use closures because each tool's JSON Schema
  (defaults, allowed namespaces) is built from settings at startup; small handler
  factories (`mcp_client/progress.py::progress_callback_for`,
  `prometheus/tools.py::query_progress_reporter`) return a configured callback.
- Keep state shapes in their own module (`investigation/workflow/state.py`), next to a constructor for
  the initial state.

## 7. Comments and docstrings

- Code explains *what* it does. A comment is for a *why* that isn't obvious
  (a workaround, an SDK quirk, a constraint).
- No comments that repeat the code, no commented-out code, no phase or history
  narration.
- MCP tool docstrings are an exception. The LLM reads them, so they describe what
  the tool returns and when to use it.

## 8. Errors

- Raise typed domain errors (`MCPUnavailableError`, `LLMError`) and map them to
  HTTP status codes in one place (`main.py` exception handlers).
- Catch a broad `Exception` only at a boundary where you convert it to a
  domain error.
- MCP tools reject bad input through the schema (`Literal`, `Field(ge=, le=)`).
  Raise `ToolError` for failures the model should see.

## 9. Types

- Type hints on every function signature. Use `dataclass(frozen=True)` for
  internal results and pydantic models for API I/O.
- Use modern syntax: `list[str]`, `X | None`.

## 10. Tests

- Every behavior change comes with a test. Name tests after the behavior:
  `test_unreachable_mcp_returns_503`.
- Unit tests make no network calls and use no real LLM. Use the fakes in
  `tests/fakes.py` (scripted chat model, in-process `MCPServer`).
- Cross-process behavior goes in `tests/integration/`.
- Async tests use anyio (`pytest.mark.anyio`), not pytest-asyncio.
- Run the full suite for both apps before you consider a change done.

## 11. Dependencies

- Pin exact versions. Runtime packages go in `requirements.txt`, which is what
  the Docker image installs. Test and dev tools go in `requirements-dev.txt`
  (`-r requirements.txt` + extras). List every package the code imports
  directly, even if it's also installed transitively.
- Verify the API of the installed version before using it. This repo uses
  **mcp 2.x**, **LangChain 1.x** and **LangGraph 1.x**, and most examples online
  are for older versions.

## 12. Automation (Makefile)

- Every developer command is a `Makefile` target (`make help` lists them).
  Don't add separate shell, PowerShell or batch scripts.
- Keep recipes to plain commands that run in any POSIX shell (Linux, macOS,
  Git Bash on Windows): no `sed -i` (GNU and BSD differ), no `jq`, no
  OS-specific branches beyond the `VENV_BIN` variable.
- If a recipe grows real logic, move it into a small Python script rather
  than writing complex shell.
- Fix machine-specific setup (PATH order, tool installs) once on the machine
  and document it in the README. Don't add workarounds to the repo.
- `.gitattributes` keeps the Makefile on LF line endings.

## 13. Containers

- Each service has its own `Dockerfile` in its folder, so Compose and
  `docker build` use just `build: ./<service>`. Keep them identical in shape:
  slim base, non-root numeric `USER 10001`, requirements installed before the
  code is copied.
- Images run as a non-root user and never contain `.env`, tests or dev
  dependencies. Keep each service's `.dockerignore` up to date.
- Secrets reach containers at runtime (`env_file`), never at build time.
- Publish ports on `127.0.0.1` only. Services talk to each other by service
  name on the compose network.
- A service listening on `0.0.0.0` must keep its host validation (for example
  `MCP_ALLOWED_HOSTS`).
- Every service has a healthcheck, and dependents wait on
  `condition: service_healthy`.

## 14. Kubernetes

- All manifests go through kustomize (`lab/kubernetes/base/kustomization.yaml`; incidents are overlays in `lab/kubernetes/incidents/`). Add new
  files to its `resources`.
- Image tags live in the manifests and in the Makefile's `TAG` variable. Change
  both together.
- Every Deployment has `app` and `version` labels, readiness and liveness
  probes, resource requests and limits, `runAsNonRoot`, a read-only root
  filesystem and all capabilities dropped.
- Configuration comes from ConfigMaps and secrets from kustomize
  `secretGenerator` fed by a gitignored `.env` file. Never commit a Secret
  manifest that contains values.
- Services find each other by Service DNS name (`http://user-service`),
  configured through ConfigMaps.
- After testing, run `make cluster-down` so the cluster stops using CPU and
  memory.

## 15. Access control for tools that touch infrastructure

- Enforce every rule in **two layers**. RBAC on the tool's Kubernetes identity
  is the hard backstop. The tool layer adds namespace allowlists, argument
  limits, output trimming and (later) per-user permissions and approval.
  Never rely on only one of them.
- The MCP server authenticates as its own ServiceAccount with short-lived
  tokens (`make mcp-kubeconfig`), never with an admin kubeconfig.
- A new tool needs its API permission added to `mcp-platform/server/deploy/` in the same
  change, with the narrowest verbs and resources that work.
- Tools return typed pydantic models (they become the MCP output schema)
  containing only the fields an on-call engineer needs. Never return raw API
  objects, environment variables or anything from a Secret.
- Keep the fake and the real system behind the same interface (`ClusterReader`,
  `ClusterWriter`, `MetricsReader`) so every tool is testable without a cluster. Never
  mix synthetic data with a real system.
- Inside an MCP server, tools are grouped by the object they act on (`k8s/pods.py`,
  `deployments.py`, `events.py`), reading and changing it in the same module, never by
  the phase that added them. Access to an external system lives in its own folder with
  the same three names: `access.py` (interfaces, errors), `<system>_api.py` (the real
  one), `fake.py` (`k8s/cluster/`, `prometheus/metrics/`). Name access objects after
  what they may do (`ClusterReader`, `ClusterWriter`), not "backend".
- Validate every value that gets put into a query language (PromQL, label
  selectors) against a strict pattern (`constants.py::NAME_PATTERN`). Never
  build a query from free text.
- Write tool errors for the model. Say what went wrong **and what to do next**
  (for example "no previous container; call again with previous=false"). A vague
  error makes the model give up on that line of investigation.
- Tool descriptions must mention non-obvious gaps in the data (for example "a
  service with no pods is missing from the overview").

## 16. Investigation graph (AI server)

- When a conclusion follows from the evidence with certainty (a service is CPU-starved,
  a service is slow now vs. was slow earlier), compute it in code
  (`helpers.computed_findings`) and state it to the LLM; don't rely on the LLM to infer
  it from raw numbers. Base each finding on two independent signals where one alone
  can mislead (throttling *and* real CPU use).

- Evidence gathering that should always happen goes in deterministic graph
  steps (`investigation/evidence/collection_steps.py`), not in the prompt. The LLM understands the
  question, reasons over evidence and writes the report. It doesn't decide the
  basic checks.
- LLM outputs that code consumes are typed with `with_structured_output(Model)`
  (`IncidentScope`, `IncidentReport`). Never parse free text.
- Every tool call is recorded as `Evidence` (with its error, if any) and
  returned by the API. A failed check is evidence, not an exception.
- Loops are capped by config (`MAX_FOLLOW_UP_ROUNDS`), and the response says
  when a cap was hit.
- A missing MCP tool degrades the investigation (step skipped and noted); it
  never breaks it.
- The graph depends on MCP tool names and result fields. Change them in
  `mcp-server` only together with `mcp_client/constants.py` (`McpTool`), `investigation/evidence/collection_steps.py`
  and `tests/fakes.py`.

## 17. Incidents and evals

- Every incident is a kustomize overlay in `lab/kubernetes/incidents/<name>`
  on top of `lab/kubernetes/base`. Never hand-edit a running cluster to set up a
  incident.
- Fault-injection code in the sample services is switched on only by an explicit
  setting (`FAULT_MODE`), defaults to off, and is clearly labelled as such.
- An incident isn't done until it's in `evals/incident_cases.py`, with a vague
  operator-style question (never naming the cause), a symptom condition and the
  expected `cause_category` / `root_cause_service`.
- Change the investigation graph or prompts only together with an eval run, and
  keep a change only if the pass rate doesn't drop. Note the before and after
  in the commit message.
- Tune reasoning with `make replay` on evidence saved by the eval (seconds), and
  repeat each case (`TIMES=5`), since one LLM answer can be luck. Finish with one
  full `make eval`.
- When the agent is wrong, read the saved evidence before touching prompts. Most
  misses so far were missing or misleading evidence, not bad reasoning.
- Report categories must be unambiguous. `cause_category` is chosen by failure
  mechanism in a fixed precedence order, and a preceding rollout never overrides
  a more specific mechanism.

## 18. Observability of the sample services

- Every service exposes `/metrics` (prometheus-fastapi-instrumentator, with
  `/health` and `/metrics` excluded) and opts in to scraping with the
  `prometheus.io/scrape|port|path` pod annotations.
- Latency histograms need buckets well past the slowest expected response
  (`LATENCY_BUCKETS_SECONDS`). A percentile can't exceed the top finite bucket.
- Detect CPU starvation with throttling (`cpu_throttled_ratio`, from cAdvisor),
  not average usage. Bursty load hides the limit in averages.
- A service must recover by itself when a dependency comes back, including
  when the dependency comes back empty. Never cache "already initialised" state
  about a remote system.
- When a call to a dependency fails, log an error that names the dependency and
  URL (`upstream unavailable: POST http://payment-service/payments`). A bare
  `502` in an access log can't be traced to its cause. Log slow calls the same
  way (`slow upstream call: … took 3.02s`).
- Keep probe and scrape requests (`/health`, `/metrics`) out of access logs. At
  a 5s scrape interval they otherwise push real traffic out of any log tail.

## 19. Tracing the AI server

- Only `ai-server/tracing/` imports Langfuse. Everything else reports through LangChain
  callbacks (graph runs, LLM calls, tools), so the tracing backend can change without
  touching the agent.
- Work that doesn't go through LangChain (such as `MCPToolbox.call`) reports itself as a
  LangChain run with the callbacks of the current config (`ensure_config()`), so it
  nests under its graph step.
- Tracing must never fail or slow down an investigation: no keys means a no-op tracer,
  and a call to the tracing backend that can fail is caught and logged.
- Tests never send traces: they run without keys or use an in-memory span exporter.
- A trace that continues a caller's work (an eval experiment item calling the AI server)
  is joined with the W3C `traceparent` header, never with custom ids.
- Eval and replay runs are recorded with Langfuse's experiment runner
  (`evals/experiment_tracking.py`), scored by plain functions (`score_correctness`), so
  runs can be compared. Use Langfuse's v2/experiments APIs; the legacy trace and
  dataset-run APIs are not available to new Langfuse organizations.
- Don't put secrets in span inputs, outputs or metadata.

## 20. Live progress and streaming

- Don't build on deprecated MCP features. MCP logging is deprecated (SEP-2577): report
  server status as progress messages (`ctx.report_progress(..., message=...)`).
- A sync backend running in a worker thread reports back to the event loop with
  `anyio.from_thread.run(...)`, through a callback parameter (`on_query_done`); backends
  never import MCP.
- Stream events come from LangChain callbacks and MCP progress into one
  `InvestigationEvents` channel; the graph doesn't know it is being streamed.
- A streaming endpoint cancels its work when the client disconnects (`finally:` in the
  generator), and reports errors as an `error` event with the same status codes and
  messages as the JSON endpoint (`errors.py`).
- Run linters per app, from that app's folder: run from another app, its local packages
  look like third-party ones and imports get reordered wrongly.

## 21. Model routing and MCP sampling

- Models are chosen through `ModelRouter` (`llm/model_router.py`), never by
  creating a second chat model in a step. Tiers are config (`LLM_MODEL`,
  `LLM_MODEL_FAST`, `FAST_MODEL_STEPS`), still `provider:model` strings.
- Move a step to the cheaper tier only with an experiment showing the pass rate holds.
  A step that decides the answer (`write_report` picks the cause category) is reasoning,
  not formatting.
- An MCP server that needs an LLM asks the client through sampling with model
  preferences; it never holds an API key or names a provider.
- A sampling resolver must ask the identical question on every round of the
  input-required round trip: build it from data that can't change between rounds
  (`RecentLogs`), and fall back to the raw data when the client can't sample.
- Sampling is capped per investigation and every sampled call is traced.

## 22. Resources, annotations and the tool policy

- Team knowledge (runbooks, service maps) lives in `mcp-platform/server/knowledge/` and is
  published as resources, not hard-coded into prompts. Keep runbooks factual: real
  dependencies and the exact log messages the services write.
- Resources are read-only and never expose secret values (env var names and
  ConfigMap/Secret names only). Validate URI parameters like tool arguments.
- Every tool is registered with annotations. The AI server only gives the agent tools
  annotated read-only; a new tool without annotations is invisible to the agent.
- Knowledge is optional evidence: a missing runbook is a note, and live evidence wins
  over documentation.

## 23. Changes to the cluster (write tools)

- The investigation is read-only. Changes are proposed in the report and run only through
  `POST /actions`, one at a time, each approved by a human (MCP elicitation).
- A write tool validates every argument before asking (exists, in bounds), asks a question
  built only from its arguments (it must be identical on the retry round), and does
  nothing unless the answer is an explicit approval. Its result says what was or wasn't
  done.
- Write tools are off by default, annotated destructive, and run with their own
  ServiceAccount with the fewest verbs that work; the read-only account never gains write
  rights.
- Replace, don't merge, when restoring a known state (rollback: JSON Patch replace of
  the pod template).
- Test write paths on the real cluster too: merge semantics and RBAC only show there.

## 24. Identity, authorization and audit

- Authenticate at the edge (API key → person), authorize where the action happens (the
  MCP server's roles), and pass the person along in a signed token, never in a plain
  header or argument the agent could set.
- Tokens are short-lived and minted per request; scopes match the job (an investigation
  never holds `k8s:write`).
- Refuse before running: authorization lives in server middleware, not inside tools.
  Checks that need the tool's answer (the approver) live in the tool, with the same policy
  object.
- Every tool call is audited, refusals included, with the trace id; the audit log is only
  appended to.
- Off-by-default security switches warn loudly at startup when off.

## 25. Several MCP servers and a gateway

- One codebase may serve several MCP servers; each process builds only the backends of
  its tool sets, so it holds only those credentials.
- The AI server sees one merged client (`McpServerGroup`); the rest of the code never
  knows how many servers there are. Duplicate tool names are a startup error.
- A gateway's naming (prefixes) stays at the edge: strip it where the client connects,
  keep plain names everywhere else.
- Coarse rules (who may reach which tools) go in the gateway; rules that need the tool's
  own data (roles with the user map, four eyes on the approver) stay in the server.
- Verify a gateway with a checklist before relying on it: tools, progress, sampling,
  elicitation, trace context, tokens. Pin its version.
- Tokens are verified with public keys (JWKS); only the issuer holds the private key.
